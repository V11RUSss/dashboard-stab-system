## 1. Что это вообще такое?

**MicroJet** — это собственный протокол обмена данными между устройствами, разработанный для управления роботизированной платформой **BRO30** (в bro_spec.json она называется «Пылесос» — это кодовое название изделия).

Протокол работает поверх обычного Ethernet, используя:
- **UDP пакеты** как транспорт
- **Multicast-адресацию** вместо unicast — то есть один пакет может принять сразу несколько устройств
- **Собственный заголовок** внутри UDP-пакета (заголовок MicroJet)

Проще говоря: устройства общаются по локальной сети, бросая UDP-пакеты в специальные multicast-группы, и все кто "подписался" на эту группу — получают данные одновременно.

## 2. Из чего состоит протокол?

```
protocol/
├── bro_spec.json          ← Главная спецификация: адреса, сообщения, устройства, параметры
├── idl/                   ← Описания структур данных на языке IDL (исходники для кодогенерации)
├── microjetlib/           ← Сгенерированная библиотека протокола (типы, заголовки, утилиты)
│   ├── inc/
│   │   ├── microjet_def.h     ← Базовые типы (статусы, коды ошибок, заголовок пакета)
│   │   ├── microjet.h         ← Главный заголовок библиотеки
│   │   ├── mjdriver_interface.h ← Интерфейс, который ДОЛЖЕН реализовать транспорт
│   │   ├── mjsysspec.h        ← Специфика системы: ID устройств, IP-адреса, ID сообщений
│   │   ├── mjtypes.h          ← Все структуры данных (результат кодогенерации из IDL)
│   │   └── mjutils.h          ← Вспомогательные функции
│   └── src/
│       ├── mjtypes.c          ← Реализация функций для работы с типами
│       └── mjutils.c          ← Реализация утилит
└── microjetlinux/         ← Реализация транспорта для Linux (работа с сокетами)
    ├── microjet_driver.h  ← Заголовок Linux-драйвера
    ├── microjet_driver.c  ← Сам Linux-драйвер (сокеты, потоки, отправка/приём)
    ├── ptp.h              ← Заголовок PTP (синхронизация времени)
    └── ptp.c              ← Реализация PTP
```

**Ключевое понимание:**
- `bro_spec.json` — это "конституция" протокола. Кодогенератор читает его и создаёт `microjetlib`
- `microjetlib` — это сгенерированный код: типы данных и готовые структуры пакетов
- `microjetlinux` — это "движок": реализует реальную отправку/приём по сети под Linux

## 3. Устройства в системе (bro_spec.json)

В системе BRO30 есть следующие устройства:

| Короткое имя | Полное название | IP адрес |
|---|---|---|
| АУФД | Автомат управления функциями движения | 10.104.0.1 |
| МУП.ТЛП | Модуль управления **левым передним** тяговым приводом | 10.102.0.2 |
| МУП.ТПП | Модуль управления **правым передним** тяговым приводом | 10.102.0.3 |
| МУП.ТЛЗ | Модуль управления **левым задним** тяговым приводом | 10.102.0.4 |
| МУП.ТПЗ | Модуль управления **правым задним** тяговым приводом | 10.102.0.5 |
| МУП.РЛ | Модуль управления **левым рулевым** приводом | 10.102.0.6 |
| МУП.РП | Модуль управления **правым рулевым** приводом | 10.102.0.7 |
| СПО | Сервисное программное обеспечение (монитор) | 10.191.0.1 |
| И.ПЫЛ | Имитатор пылесоса | 10.192.0.2 |

> **МУП (Модуль управления приводом)** — это встроенный контроллер двигателя. Получает команды, управляет приводом, отдаёт телеметрию.
> **АУФД** — главный управляющий компьютер, который командует всеми МУП.
> **СПО** — сервисный монитор (ваш Dashboard).

## 4. Как данные передаются по сети?

### Multicast — "широковещание в группу"

Вместо того чтобы посылать каждому устройству отдельно (unicast), в системе используется **multicast**: пакет отправляется на специальный групповой IP-адрес, и его получают все устройства, которые "подписались" на этот адрес через IGMP.

В системе определено несколько multicast-групп:

| Имя канала | IP адрес | Порт | Назначение |
|---|---|---|---|
| srv_mcast_req | 239.200.200.1 | 49001 | Запросы (параметры, команды, сообщения) |
| srv_mcast_ans | 239.200.200.1 | 49002 | Ответы на запросы |
| bro_bup_ctrl_mcast | 239.200.10.1 | 49001 | Управление приводами (команды движения) |
| bro_bup_data_mcast | 239.200.10.1 | 49002 | Состояние приводов (bup_state) |
| bro_bup_srv_mcast | 239.200.100.1 | 49001 | Сервисный канал (телеметрия, отладка, PTP) |
| im_bro_drive_mcast | 239.200.90.1 | 49001 | Данные имитатора |

### Схема потока данных

```
  АУФД (10.104.0.1)
       │
       ├──[bup_ctrl]──► 239.200.10.1:49001  ──► МУП.ТЛП, МУП.ТПП, МУП.ТЛЗ... (команды движения)
       ├──[prm_req]───► 239.200.200.1:49001 ──► МУП (запросы параметров)
       ◄──[bup_state]── 239.200.10.1:49002 ◄── МУП (состояние привода)
       ◄──[prm_ans]──── 239.200.200.1:49002 ◄── МУП (ответы на параметры)

  СПО (10.191.0.1) — Dashboard
       ◄──[dcu_tel]──── 239.200.100.1:49001 ◄── МУП (телеметрия каждые 250 мкс)
       ◄──[bup_state]── 239.200.10.1:49002 ◄── МУП
       ◄──[ptp_state]── 239.200.100.1:49001 ◄── МУП (синхронизация каждые 500 мс)
       ├──[bup_srv_ctrl]► 239.200.100.1:49001 ──► МУП (управление в сервисном режиме)
```

## 5. Формат пакета MicroJet

Каждый пакет MicroJet — это обычный Ethernet-кадр с таким содержимым:

```
┌──────────────────────────────────────┐
│  Ethernet Header (14 байт)           │  MAC src + MAC dst + Type IP
├──────────────────────────────────────┤
│  IP Header (20 байт)                 │  IPv4, Protocol=UDP
├──────────────────────────────────────┤
│  UDP Header (8 байт)                 │  src_port, dst_port, len, checksum
├──────────────────────────────────────┤
│  MicroJet Header (16 байт)           │  ← ЭТО СОБСТВЕННЫЙ ЗАГОЛОВОК
│  ┌──────┬──────┬──────┬──────┐        │
│  │ src  │ dst  │  id  │ cnt  │        │  src/dst — ID устройств (2 байта)
│  │ 2 б  │ 2 б  │ 2 б  │ 2 б  │        │  id — ID типа сообщения
│  ├──────┴──────┴──────┴──────┤        │  cnt — счётчик (порядковый номер)
│  │  ts_s (4 байта)           │        │  ts_s — время отправки (секунды)
│  ├───────────────────────────┤        │  ts_ns — время отправки (наносекунды)
│  │  ts_ns (4 байта)          │        │
│  └───────────────────────────┘        │
├──────────────────────────────────────┤
│  Payload (данные сообщения)           │  например: bup_drv_state_t, dcu_telemetry_t
└──────────────────────────────────────┘
```

### ID устройств (из mjsysspec.h)

```c
BRO30_AUFD        = 0xF5B6   // АУФД
BRO30_DCU         = 0xB8FE   // МУП (базовый)
BRO30_BUP_DCU_LFD = 0xFA82   // МУП левый передний
BRO30_BUP_DCU_RFD = 0xD334   // МУП правый передний
BRO30_BUP_DCU_LRD = 0x57F6   // МУП левый задний
BRO30_BUP_DCU_RRD = 0x7E40   // МУП правый задний
BRO30_BUP_DCU_LST = 0x7659   // МУП левый рулевой
BRO30_BUP_DCU_RST = 0x5FEF   // МУП правый рулевой
BRO30_MON         = 0x6C99   // СПО (Dashboard)
BRO30_ALL         = 0xFFFF   // Широковещание всем
```

### ID сообщений (из mjsysspec.h)

```c
ID_PRM_REQ           = 0xB4E1   // Запрос параметра
ID_PRM_ANS           = 0xFCC8   // Ответ на запрос параметра
ID_CMD_REQ           = 0x7E7A   // Запрос команды
ID_CMD_ANS           = 0xFB98   // Ответ на команду
ID_DCU_TEL           = 0xD63C   // Телеметрия МУП
ID_BUP_STATE         = 0x0824   // Состояние привода
ID_BUP_CTRL          = 0xD994   // Управление приводом
ID_BUP_MULTI_CONTROL = 0x76A9   // Управление несколькими приводами
ID_PTP_STATE         = 0xD950   // Состояние синхронизации PTP
ID_FORMULAR          = 0x10AD   // Электронный формуляр
```

## 6. IDL — откуда берутся типы данных

**IDL (Interface Description Language)** — это простой язык описания структур данных, понятный людям. Файлы в папке `idl/` — это **исходники**, из которых генерируется код библиотеки.

### Пример IDL файла (bup_drv_state.idl)

```idl
@doc('Состояние привода наведения БУП')
struct bup_drv_state
{
    @doc('Способ управления приводом')
    @alias('drv_ctrl_mode')    // ← ссылка на enum drv_ctrl_mode
    int8 mode;

    @doc('Угловое положение в локальной СК, рад. От -pi до pi')
    float angle;

    @doc('Угловая скорость в локальной СК, рад/с')
    float speed;
    // ...
};
```

**После кодогенерации это превращается в (mjtypes.h):**

```c
typedef struct bup_drv_state
{
    /** alias: drv_ctrl_mode_t — используй enum drv_ctrl_mode_k для интерпретации */
    int8_t mode;
    float angle;       // радианы, от -π до π
    float speed;       // рад/с
    // ...
} bup_drv_state_t;
```

### Как работают `@alias`

Поле с аннотацией `@alias('drv_ctrl_mode')` означает: это поле нужно интерпретировать через соответствующий enum:

```c
// Если mode == 4:
drv_ctrl_mode_k mode_enum = (drv_ctrl_mode_k)state.mode;
// mode_enum == DRV_CTRL_MODE_ANGLE  →  "Приведение на заданный угол"
```

> **IDL файлы не нужно редактировать руками** — их читает кодогенератор. Если нужно добавить поле — правится IDL, потом кодогенератор обновляет `mjtypes.h`.

## 7. microjetlib — главная библиотека

Это **сгенерированный код** протокола. Он не зависит от ОС — работает и на Linux, и на STM32.

### `microjet_def.h` — базовые типы

```c
// Статусы операций
MJ_OK   = 0    // всё хорошо
MJ_FAIL = -1   // что-то пошло не так

// Результаты обработки принятого пакета
MJ_ACCEPT      // пакет принят и обработан
MJ_REJECT_SRC  // отвергнут: неверный источник
MJ_REJECT_DST  // отвергнут: неверный получатель
MJ_REJECT_ID   // отвергнут: неверный ID сообщения
MJ_PROC_FAIL   // ошибка при обработке

// Состояния сообщений
MJ_MSG_ACTUAL    // данные актуальны (свежие)
MJ_MSG_OBSOLETE  // данные устарели
```

### `mjdriver_interface.h` — контракт с транспортом

Это самый важный файл для понимания архитектуры. Он описывает **интерфейс**, который любой транспортный слой **обязан реализовать**:

```c
typedef struct mj_udp4_transport_interface {
    uint8_t*    (*alloc)(uint16_t size);             // выделить память под пакет
    void        (*free)(uint8_t *ptr);               // освободить память
    void*       (*create_interface)(...);            // зарегистрировать Ethernet интерфейс
    mj_status_t (*register_callback)(...);           // подписаться на входящие пакеты
    void*       (*create_out_pkt)(...);              // создать исходящий UDP пакет
    void        (*tx)(void *pkt, cb);                // отправить пакет
    uint8_t*    (*get_payload)(void *pkt);           // получить указатель на данные
    void        (*set_payload)(void *pkt, ...);      // установить данные пакета
    void        (*join_group)(void*, uint32_t);      // вступить в multicast группу
    void        (*pool_tx)(void);                    // (опционально) flush буфера
} mj_udp4_transport_interface_t;
```

**Смысл:** `microjetlib` работает с любым транспортом через эти указатели на функции. Она не знает, как именно работают сокеты — за неё это делает `microjetlinux`.

### `mjsysspec.h` — специфика системы BRO30

Содержит готовые константы (IP, ID устройств, ID сообщений, ID параметров — всё в одном месте).

### `mjtypes.h` — все структуры данных

Гигантский файл (~1300 строк) со всеми типами данных:
- Перечисления (`drv_ctrl_mode_k`, `dcu_status_k`, `drv_ctrl_error_k`...)
- Структуры (`bup_drv_state_t`, `dcu_telemetry_t`, `bup_drv_control_t`...)
- Готовые структуры сообщений со встроенным заголовком MicroJet

## 8. microjetlinux — реализация транспорта под Linux

Реализует интерфейс `mj_udp4_transport_interface_t` для Linux, работая с RAW сокетами на уровне Ethernet.

### Почему RAW сокеты, а не обычные UDP?

С RAW сокетами (`PF_PACKET, SOCK_RAW`) драйвер полностью контролирует каждый байт пакета:
- Можно задать свои MAC-адреса
- Получать точные временные метки от сетевого интерфейса (нужно для PTP)
- Отправлять IGMP join-сообщения вручную

### Архитектура потоков

```
Главный поток
    ├── init_mjdrv()       ← инициализация: создание RAW сокетов
    │
    ├── TX поток (CPU ядро 3, SCHED_FIFO, высокий приоритет)
    │       └── каждые 250 мкс:
    │               1. вызов p_loop_fcn()    ← ваша бизнес-логика
    │               2. вызов p_fcn()         ← отправка пакетов MicroJet
    │               3. вызов ptp_tick_fcn()  ← тики PTP (если включён)
    │               4. sleep до следующего тика (clock_nanosleep)
    │
    └── RX поток (CPU ядро 1, SCHED_FIFO, максимальный приоритет)
            └── бесконечно:
                    poll() → recvfrom() → bufferHandler() → callback()
```

### Ключевые функции драйвера

```c
// Задать имя сетевого интерфейса ПЕРЕД инициализацией
void setEthernetInterfaceName(char * name);  // "eth0", "enp3s0", ...

// Инициализация (заполняет idrv и открывает сокеты)
void init_mjdrv(mj_drv_interface_t * idrv);

// Запуск/остановка приёма и передачи
void setTxStatus(bool value);
void setRxStatus(bool value);

// Установить функцию основного цикла (вызывается каждый тик 250 мкс)
void mj_set_loop_fcn(void (*loop_fcn)(void));

// Включить/выключить PTP
void setPtpStatus(bool value);

// Деинициализация / переинициализация
void deinit_mjdrv();
void reinit_mjdrv();
```

### Как работает приём пакета

```
Сетевой интерфейс получает Ethernet кадр
    ↓
RX поток: poll() → recvfrom() → буфер recieve_buffer[1024]
    ↓
bufferHandler(buffer, ...)
    ├── Проверяет: protocol == UDP?
    ├── Проверяет: src_ip != наш IP? (не свои пакеты)
    ├── Проверяет: dst_ip совпадает с одним из зарегистрированных?
    └── Проверяет: dst_port совпадает?
    ↓ (если всё совпало)
callback(payload, size, timestamp_sec, timestamp_ns)
    ↓
microjetlib обрабатывает заголовок MicroJet,
проверяет ID сообщения, обновляет буферы данных
```

## 9. Синхронизация времени (PTP)

**PTP (Precision Time Protocol, IEEE 1588)** — протокол точной синхронизации времени по сети с точностью до микросекунд.

### Зачем?

МУП отправляет телеметрию с временными метками. Если часы МУП и часы Dashboard разошлись — данные на временной оси будут неверными. PTP исправляет это.

### Как работает обмен для синхронизации

```
MASTER (Linux PC)                    SLAVE (МУП)
     │
     │──Announce──────────────────────► │  (сообщаю: я мастер)
     │──Sync (с меткой t1)────────────► │  (посылаю время)
     │──Follow_Up (точный t1)─────────► │  (уточняю метку)
     │                   ◄──Delay_Req── │  (t3: я отправил запрос)
     │──Delay_Resp (t4)───────────────► │  (t4: когда я получил)
     │
     │  Slave вычисляет:
     │    offset = ((t2-t1) - (t4-t3)) / 2
     │    delay  = ((t2-t1) + (t4-t3)) / 2
     │  И корректирует свои часы
```

### Состояния порта PTP

```
INITIALIZING → LISTENING
                   ├──► SLAVE    (получен Announce от мастера вовремя)
                   └──► PASSIVE  (получен Announce, но с опозданием)

setPtpStatus(true) → MASTER  (Linux PC берёт на себя роль мастера)
```

### Включение PTP в коде

```c
// После init_mjdrv():
setPtpStatus(true);  // активирует MASTER режим
ptp_init(&drv);      // создаёт PTP пакеты и регистрирует callbacks
```

## 10. Как работают параметры?

Параметр — это именованное значение (float, int, bool, string) которое можно **читать** и **записывать** на устройстве.

### Чтение параметра

```
СПО → [srv_mcast_req] → parameter_request_t {
    type = PARAMETER_REQUEST_TYPE_READ,
    id   = PRM_FLOAT_CUR_LIM,  // хэш имени параметра = 0x55DA9773
    val  = {}                   // пустое при чтении
}

МУП → [srv_mcast_ans] → parameter_answer_t {
    id  = PRM_FLOAT_CUR_LIM,
    ans = PARAMETER_STATUS_OK,
    val = [00 00 BE 42 ...]     // float 95.0, little-endian, затем padding
}
```

### Запись параметра

```
СПО → [srv_mcast_req] → parameter_request_t {
    type = PARAMETER_REQUEST_TYPE_WRITE,
    id   = PRM_BOOL_SERVICE_MODE,  // = 0x311FD2BA
    val  = [01 00 00 ...]           // первый байт bool = true
}
```

`val` — это буфер на 32 байта, а не универсальная строка. Тип известен из
имени/описания параметра и `mjsysspec.h`:

- `PRM_BOOL_*` — C `bool`, используется первый байт;
- `PRM_FLOAT_*` — IEEE-754 `float`, первые 4 байта little-endian;
- `PRM_INT_*` — знаковый `int32`, первые 4 байта little-endian;
- `PRM_STRING_*` — строка до 31 байта с нулём в конце (на текущем стенде CP866).

Остаток буфера заполняется нулями. Передача текста `"95.0"` вместо бинарного
float была бы ошибкой: микроконтроллер получил бы совсем другой набор байтов.

### Идентификаторы параметров

Каждый параметр идентифицируется **хэшем своего имени**. Все хэши определены в `mjsysspec.h`:

```c
PRM_FLOAT_CUR_LIM      = 0x55DA9773  // ограничение тока
PRM_FLOAT_OCP_LVL      = 0x4A0AB355  // уровень защиты по току
PRM_BOOL_SERVICE_MODE  = 0x311FD2BA  // сервисный режим
PRM_FLOAT_DRV_LIMIT_UP = 0x5C57D2B7  // верхний предел наведения
// ... и так далее для каждого из параметров
```

## 11. Как работают команды?

Команда — это запрос на выполнение действия. Ответ может приходить несколько раз (пока команда выполняется).

```
СПО → МУП: command_request_t { type = COMMAND_TYPE_SAVEPRM }

МУП → СПО: command_answer_t {
    command = COMMAND_TYPE_SAVEPRM,
    state   = COMMAND_STATE_INPROGRESS,  // ещё выполняется
    request_counter = 1
}

МУП → СПО: command_answer_t {
    command = COMMAND_TYPE_SAVEPRM,
    state   = COMMAND_STATE_DONE,        // готово
    request_counter = 1,
    info    = "OK"
}
```

### Список команд

| Команда | Описание |
|---|---|
| `SWRESET` | Программная перезагрузка |
| `SAVEPRM` | Сохранить параметры в ПЗУ |
| `SET_HOME_POSITION` | Текущее положение = нулевое |
| `SET_UP_LIMIT` | Текущее положение = верхний предел |
| `SET_DOWN_LIMIT` | Текущее положение = нижний предел |
| `SET_EL_ZERO` | Установить нулевое положение ротора |
| `OPERATION_TIME_RESET` | Сброс счётчика наработки |
| `INTEGRATOR_RESET` | Сброс интегратора ПИД |
| `FIRMWARE_UPGRADE` | Перейти в режим обновления прошивки |
| `FIRMWARE_VERIFY` | Подтвердить успешное обновление |
| `CURRENT_SENSOR_CALIB` | Калибровка датчиков тока |

## 12. Как работает телеметрия?

Телеметрия — данные, которые МУП **периодически рассылает сам**, без запроса.

| Сообщение | Период | Канал | Содержимое |
|---|---|---|---|
| `dcu_tel` | 250 мкс | bro_bup_srv_mcast | Полная телеметрия (ток, напряжение, угол, ПИД) |
| `bup_state` | По событию | bro_bup_data_mcast | Краткое состояние привода |
| `ptp_state` | 500 000 мкс (500 мс) | bro_bup_srv_mcast | Статистика синхронизации |
| `dbg` | 1000 мкс (1 мс) | bro_bup_srv_mcast | Отладочные значения |

## 13. Как подключить этот транспорт к своему приложению

### Шаг 1: Включить заголовки

```c
#include "microjetlib/inc/microjet.h"
#include "microjetlib/inc/mjsysspec.h"
#include "microjetlib/inc/mjtypes.h"
#include "microjetlinux/microjet_driver.h"
#include "microjetlinux/ptp.h"
```

### Шаг 2: Инициализация

```c
mj_drv_interface_t drv;

setEthernetInterfaceName("eth0");  // задайте имя интерфейса ДО init
init_mjdrv(&drv);                  // открывает сокеты и заполняет интерфейс драйвера
```

### Шаг 3: Подписаться на входящую телеметрию

```c
mj_msg_proc_res_t on_dcu_telemetry(
    uint8_t* payload, uint16_t size, uint32_t ts_s, uint32_t ts_ns)
{
    // В payload: MicroJet заголовок (16 байт) + dcu_telemetry_t
    mj_msg_header_t * hdr = (mj_msg_header_t*)payload;
    dcu_telemetry_t  * tel = (dcu_telemetry_t*)(payload + sizeof(mj_msg_header_t));

    printf("Угол: %.3f рад, Скорость: %.3f рад/с\n",
           tel->load_sens_angle, tel->load_sens_speed);
    return MJ_ACCEPT;
}

// Регистрируем callback
drv.udp4.register_callback(
    BRO_BUP_SRV_MCAST_IP,  // 239.200.100.1 (в network byte order)
    htons(49001),
    on_dcu_telemetry
);
```

### Шаг 4: Запустить приём и передачу

```c
setRxStatus(true);  // разрешить обработку приёма
setTxStatus(true);  // разрешить передачу
```

Регистрация первого входящего callback запускает RX-поток `microjetlinux`.
Старый пример библиотеки мог отдельно запускать `transmitFunction()` для
250-микросекундного tick. Текущий Gateway этого не делает: он вызывает
generated `mon.loop()` и `mon.tick()` из собственного управляемого потока.
Так завершение и безопасный `OFF` не зависят от отмены чужого pthread.

## 14. Как Dashboard отправляет команды

Frontend не собирает MicroJet-пакеты. Он посылает Backend понятное JSON-действие
с именем выбранной карточки. Backend проверяет действие и превращает значение
параметра в типизированные байты. Затем по существующему TCP-соединению команда
попадает в Gateway, а Gateway вызывает generated API `mj_mon`.

```text
карточка МУП.ТЛП
  → WebSocket JSON: read_parameter / execute_command / service_start
  → Backend: проверка устройства, ID и типа
  → внутренний control frame на TCP 8888
  → Gateway: generated cmd_req/msg_req/prm_req/bup_srv_ctrl
  → multicast MicroJet
  → только МУП.ТЛП, потому что hdr.dst = BRO30_BUP_DCU_LFD
```

`BRO30_ALL = 0xFFFF` остаётся частью протокола и означает «всем устройствам»,
но Dashboard его для управления не предлагает и не отправляет. Это защищает
от случайной одновременной команды всем шести приводам.

Одноразовые запросы подтверждаются дважды: сначала `control_ack` от Gateway
показывает, что пакет проверен и отправлен, затем `cmd_ans`, `msg_ans` или
`prm_ans` сообщает результат самого контроллера. `formular` приходит отдельным
полным сообщением.

`bup_srv_ctrl` generated-библиотека формирует каждые 20 мс (50 Гц). Для него
действует lease: Backend посылает keepalive, а Gateway при его потере сначала
выдаёт `OFF`, потом прекращает периодическую передачу.

### Шаг 5: (опционально) Включить PTP

```c
setPtpStatus(true);
ptp_init(&drv);
```
