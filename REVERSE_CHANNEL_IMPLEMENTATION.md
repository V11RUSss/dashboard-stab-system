# Что сделано для обратного канала Dashboard → МУП

Этот документ простыми словами описывает работу, выполненную после согласования
экрана управления. Он относится только к обратным пакетам, ответам на них и
связанному интерфейсу. Виртуальная пара `veth0 ↔ veth1` не создавалась, не
удалялась и не перенастраивалась.

## 1. Что было до изменений

Проект умел передавать данные только в одну сторону:

```text
МУП / Fake Monitor → Gateway → Backend → Frontend
```

Gateway принимал `dcu_tel` и `bup_state`, но не читал данные от Backend. Backend
читал TCP-соединение с Gateway, но ничего не мог записать в него. Поэтому кнопка
во Frontend не могла дойти до MicroJet.

В generated-библиотеке нужные функции уже были:

- `cmd_req.tx(dst)` — отправить одну команду;
- `msg_req.tx(dst)` — попросить устройство выдать сообщение;
- `prm_req.tx(dst)` — прочитать или записать параметр;
- `bup_srv_ctrl` — периодический сервисный пакет управления.

Именно эти готовые функции теперь используются. Форматы настоящих MicroJet
сообщений не были придуманы заново.

## 2. Как теперь идёт команда

```text
Frontend
  → WebSocket JSON
Backend
  → короткий внутренний control frame
  → то же TCP-соединение, порт 8888
Gateway
  → generated mj_mon
  → настоящий MicroJet Ethernet/UDP пакет
МУП или Fake Monitor
```

Ответ проходит в обратную сторону:

```text
МУП → cmd_ans / msg_ans / prm_ans / formular
Gateway → внутренний TLV
Backend → декодирование и WebSocket
Frontend → «Последние ответы» в карточке устройства
```

## 3. Почему `DST=ALL` нет в интерфейсе

`DST=ALL`, или `0xFFFF`, означает «сообщение предназначено всем устройствам».
Для диагностического чтения это иногда удобно, но для перезагрузки, записи во
flash или управления приводом это слишком опасно.

Поэтому назначение берётся из открытой карточки. Карточка `МУП.ТЛП` всегда даёт
`dst=0xFA82`, `МУП.ТПП` — `0xD334` и так далее. Backend и Gateway отдельно
проверяют, что ID входит ровно в список шести МУП. Значение `0xFFFF` они не
пропускают.

## 4. Внутренний протокол Backend → Gateway

Это не MicroJet и не Ethernet-пакет. Это маленькая служебная оболочка только
для двух процессов проекта. Все числа little-endian.

```text
uint32 magic       = "MJC1"
uint8  version     = 1
uint8  opcode
uint16 dst_id
uint32 request_id
uint16 body_length
bytes  body[body_length]
```

Есть семь операций: команда, запрос сообщения, параметр, START сервиса,
UPDATE сервиса, STOP сервиса и keepalive. Максимальное тело — 64 байта. Gateway
проверяет magic, версию, длину, целевой ID и допустимые значения.

Файлы: `gateway/src/control_protocol.hpp`, `gateway/src/tcp_forwarder.*` и
`backend/core/control_service.py`.

## 5. Использование generated MicroJet

В `gateway/src/real_receiver.cpp` вместо отдельных самодельных сетевых пакетов
инициализируется полный generated `mj_mon` из
`gateway/microjetlib/mon/mj_mon_spec.c`.

Gateway вызывает готовые generated-методы. Благодаря этому библиотека сама
ставит правильные ID сообщений, адрес multicast, порт, счётчик и timestamp.
Gateway передаёт только выбранный `dst` и поля запроса.

Generated `bup_srv_ctrl` по умолчанию включён и имеет `dst=ALL`. Сразу после
инициализации Gateway принудительно меняет это на безопасное состояние:

```text
tx_enable = false
dst = NONE
mode = OFF
```

Без явного `service_start` из Backend ни один сервисный пакет не отправляется.

## 6. Команды

Frontend показывает все 11 команд из generated enum: `SWRESET`, `SAVEPRM`,
установку нулей/пределов, сброс интеграторов, операции прошивки и калибровку
датчиков тока. Перед отправкой появляется подтверждение.

Команда отправляется один раз. `control_ack` означает только «Gateway проверил
и отправил пакет». Настоящий результат устройства приходит позже в `cmd_ans`:
`INPROGRESS`, `DONE`, `FORBITTEN`, `ERROR` и так далее.

`SAVEPRM` дополнительно вынесена отдельной кнопкой «Сохранить во flash» рядом с
параметрами.

## 7. Параметры

Каталог не продублирован вручную. Backend при запуске объединяет:

- описания, единицы и набор параметров устройства `dcu` из `bro_spec.json`;
- generated ID и типы `PRM_BOOL_*`, `PRM_FLOAT_*`, `PRM_INT_*`,
  `PRM_STRING_*` из `mjsysspec.h`.

Состав читается из generated-массива `_prm_ids[71]`. Получается 71 параметр
для каждой из шести одинаковых карточек МУП: 64 рабочих параметра из
`dcu.parameters` и 7 системных (`dev_id` и настройки multicast-интерфейсов).

Поле `val[32]` передаётся бинарно:

- bool — 0 или 1 в первом байте;
- float — 4 байта IEEE-754 little-endian;
- int — 4 байта `int32` little-endian;
- string — до 31 байта CP866 и нулевой конец.

Остаток заполняется нулями. При чтении Backend делает обратное преобразование и
показывает понятное значение. Кнопка «Прочитать все» отправляет 71 отдельный
адресный запрос с небольшой паузой, а не один неизвестный пакет.

В Docker файлы спецификации подключаются Backend только для чтения в каталог
`/app/protocol`. Исходные generated-файлы остаются единственным источником ID.

## 8. Запрос сообщений

Из интерфейса можно запросить два непериодических полезных сообщения:

- `bup_state` — краткое состояние привода;
- `formular` — электронный формуляр.

Периодическое `dcu_tel` через `msg_req` не запрашивается: устройство и так
посылает его постоянно, а спецификация для периодического сообщения может
ответить `ISPERIODIC`.

## 9. Сервисное управление 50 Гц

Период задан generated-спецификацией: 20 000 мкс, то есть 20 мс или 50 Гц.
Frontend не генерирует 50 WebSocket-сообщений в секунду. Он отправляет START или
UPDATE только при действии пользователя, а стабильный период создаёт Gateway.

Поля: режим, угол, скорость, напряжение и ток. Одновременно может работать
только один выбранный привод и одна вкладка-владелец.

Добавлены три уровня защитной остановки:

1. При нормальном STOP Gateway ставит `mode=OFF`, обнуляет задания, отправляет
   как минимум два последних OFF-пакета и выключает периодическую передачу.
2. Backend каждые 400 мс продлевает lease. Если keepalive пропал, Gateway сам
   выполняет безопасный STOP примерно через одну секунду.
3. Закрытие вкладки-владельца, разрыв TCP, завершение Backend или Gateway также
   приводит к STOP. Эта защита находится в Gateway и не зависит от Frontend.

## 10. Ответы и их декодирование

Gateway теперь пересылает не только телеметрию, но и:

| Ответ | TLV type | Размер payload |
|---|---:|---:|
| `cmd_ans` | `0x03` | 44 байта |
| `msg_ans` | `0x04` | 12 байт |
| `prm_ans` | `0x05` | 40 байт |
| `formular` | `0x06` | 264 байта |
| локальный `control_ack` | `0x10` | 8 байт |

`backend/core/mj_decoder.py` проверяет точный размер и разбирает generated
layout. Ответ параметра дополнительно связывается с каталогом, чтобы 32 байта
превратились в правильный bool, float, int или string.

## 11. Что изменилось во Frontend

Во вкладке «Устройства» осталось ровно шесть физических карточек. В каждой
теперь три раздела:

1. «Состояние» — прежняя телеметрия.
2. «Команды и параметры» — разовые generated-команды, два запроса сообщений,
   чтение и запись 71 параметра, чтение всех параметров и SAVEPRM.
3. «Управление 50 Гц» — запуск непрерывного потока, изменение уже активного
   потока и его остановка с отправкой OFF.

Это разделение соответствует не количеству кнопок, а трём разным сценариям:
просмотр состояния, разовые операции и непрерывное управление. Четыре
generated-типа `cmd_req`, `msg_req`, `prm_req`, `bup_srv_ctrl` не являются
четырьмя командами. Например, внутри `cmd_req` находится 11 кодов команд, а
`prm_req` работает с отдельным каталогом из 71 настройки.

Список сообщений показан сразу радиокнопками. Поиск есть только у большого
каталога из 71 параметра; списки команд и режимов открываются без поисковой
строки. У выбранной команды и режима 50 Гц отображается простое описание. В
режиме 50 Гц поля, которые не относятся к выбранному режиму, отключаются.
Кнопка изменения потока доступна только после старта, а кнопка остановки явно
подписана «Остановить поток (OFF)».

Каталог больше не зависит от единственного сообщения при открытии страницы.
Пока каталог не загружен, Frontend раз в 0,5 секунды запрашивает единое событие
`control_context`, в котором Backend атомарно передаёт и каталог, и актуальное
состояние управления. Поэтому поток телеметрии не может окончательно вытеснить
список команд, параметров или режимов до того, как Dash успеет его обработать.
После успешной загрузки полного каталога Frontend запрашивает только маленький
`control_snapshot` раз в 5 секунд: options больше не переустанавливаются,
открытый список и введённый пользователем поиск не сбрасываются. После любой
команды актуальный snapshot всё равно рассылается немедленно.

При первой загрузке Dash может временно очистить значение списка, пока его
`options` ещё пусты. Поэтому вместе с каталогом Frontend теперь восстанавливает
безопасные допустимые значения по умолчанию: `INTEGRATOR_RESET` для разовой
команды, `formular` для запроса сообщения и `OFF` для потока 50 Гц.

Карточки создаются один раз. При телеметрии обновляется только содержимое
раздела состояния. Поэтому выбранный параметр, введённое число и открытый
раздел больше не сбрасываются два раза в секунду.

Высокочастотные WebSocket-события маршрутизируются в браузере. Кадры графика
не вызывают Python-callback карточек или редактора скриптов. Полное содержимое
карточки обновляется один раз в секунду, а ONLINE/OFFLINE считается отдельно
в браузере по каждому `devices_batch`. Поэтому очередь Dash не может заставить
работающее устройство мигать как отключённое. Протокольное поле `status`
остаётся в разделе состояния и не подменяет индикатор доступности.

Опасные операции требуют подтверждения браузера. Светлая и тёмная темы
используют те же Bootstrap-переменные, что и остальная панель.

## 12. Изменения Linux-драйвера

В `microjetlinux` добавлен явный признак реально запущенного RX/TX-потока.
Деинициализация больше не пытается отменить несуществующий поток. Сокеты при
старте получают значение `-1`, а ошибки инициализации корректно его сохраняют,
чтобы Gateway не продолжил работу с уже закрытым файловым дескриптором.

## 13. Проверки

Добавлены проверки:

- формат и little-endian внутреннего control frame;
- запрет `dst=ALL`;
- построение каталога из generated-спецификации;
- бинарная упаковка параметров;
- STOP при закрытии вкладки-владельца;
- декодирование `cmd_ans`, `msg_ans`, `prm_ans`, `formular`, `control_ack`;
- запись обратного фрейма в то же TCP-соединение;
- сборка Gateway с generated MON и существующие тесты TLV.

Команды локальной проверки:

```bash
cmake -S gateway -B /tmp/bro30-gateway-build \
  -DREAL_MODE=ON -DBUILD_TESTING=ON -DCMAKE_BUILD_TYPE=Debug
cmake --build /tmp/bro30-gateway-build --parallel 4
ctest --test-dir /tmp/bro30-gateway-build --output-on-failure

PYTHONPATH=backend python3 -m unittest discover -s backend/tests -v
python3 -m py_compile frontend/main.py frontend/tabs/devices.py
```

## 14. Ограничение Fake Monitor

В репозитории Fake Monitor доступен как готовый ELF-бинарник, а не исходный
код. В нём видны обработчики входящих `cmd_req`, `msg_req`, `prm_req` и
`bup_srv_ctrl`, поэтому транспорт можно проверить на виртуальной паре. Но без
исходников нельзя гарантировать, что каждая кнопка действительно изменит его
внутреннюю модель именно так же, как настоящий микроконтроллер.

Поэтому тест состоит из двух частей: программные тесты точно проверяют байты и
маршрутизацию, а окончательная проверка поведения конкретной команды делается
на запущенном Fake Monitor или реальном МУП по его ответу.

### Результат проверки на текущем стенде

При запущенном Fake Monitor на `veth0` и Gateway на `veth1` проверено:

- входящий поток около 4000 `dcu_tel` в секунду идёт без ошибок размера, ID,
  источника или timestamp;
- адресный `read_parameter(service_mode)` для `МУП.ТЛП` получил сначала
  `control_ack=SENT`, затем настоящий `prm_ans=OK` со значением `false`;
- короткий `service_start` в безопасном режиме `OFF` с нулевыми заданиями
  получил `SERVICE_STARTED`, а явный STOP — `SERVICE_STOPPED`;
- `msg_req(formular)` был принят и отправлен Gateway (`control_ack=SENT`), но
  этот Fake Monitor не вернул `msg_ans/formular` за 5 секунд. Это ограничение
  текущего эмулятора; транспорт запроса и generated-счётчик при этом проверены.

Во время теста конфигурация `veth0/veth1` не изменялась.
