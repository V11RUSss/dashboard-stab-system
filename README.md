# BRO30 Dashboard

Инженерная панель мониторинга и сервисного управления MicroJet BRO30. Проект
принимает телеметрию, записывает выбранные сессии и через тот же Gateway
отправляет адресные команды, запросы параметров и `bup_srv_ctrl`.

## Архитектура

```text
BRO30 / Fake Monitor
  ↔ raw Ethernet + IPv4/UDP + MicroJet
  ↔ C++ Gateway
  ↔ внутренний TCP, порт 8888
  ↔ Python Backend
  → WebSocket schema v1, порт 8765
  ↔ Dash Frontend, порт 8050
```

| Компонент | Роль |
|---|---|
| `gateway` | Принимает MicroJet, пересылает телеметрию/ответы и формирует исходящие пакеты через generated `mj_mon` |
| `backend` | Декодирует generated C-layout, агрегирует телеметрию, проверяет управляющие действия и типы параметров |
| `frontend` | Показывает графики и шесть устройств, даёт адресно читать/писать параметры, выполнять команды и включать сервисное управление |

Главные источники истины по протоколу, в порядке приоритета:

1. `gateway/bro_spec.json`;
2. `gateway/microjetlib`;
3. `main.pdf`;
4. `PROTOCOL_DOCUMENTATION.md` как поясняющий документ.

## Текущий тестовый интерфейс

Локальный стенд использует временную виртуальную пару:

```text
Fake Monitor → veth0 ↔ veth1 → Gateway
```

В `deploy/docker-compose.yml` Gateway намеренно настроен на `veth1`. Эта
настройка не переключает трафик на физическую сетевую карту.

Проверить уже созданную пару:

```bash
ip link show veth0
ip link show veth1
```

Проект не создаёт, не удаляет и не перенастраивает эту пару автоматически.

## Поддерживаемый входящий протокол

| Сообщение | MicroJet ID | Payload | Период |
|---|---:|---:|---:|
| `dcu_tel` | `0xD63C` | 236 байт (235 полей + 1 tail padding) | 250 мкс |
| `bup_state` | `0x0824` | 60 байт | по событию |
| `cmd_ans` | `0xFB98` | 44 байта | ответ на команду |
| `msg_ans` | `0xD80F` | 12 байт | ответ на запрос сообщения |
| `prm_ans` | `0xFCC8` | 40 байт | ответ на параметр |
| `formular` | `0x10AD` | 264 байта | по запросу |

Это не два разных устройства. Каждый из шести физических приводов
`bup_dcu_*` может отправлять оба сообщения со своим одинаковым `src_id`:
частую подробную телеметрию `dcu_tel` и редкое краткое состояние `bup_state`.
Backend хранит их внутри одной карточки устройства раздельно по `msg_type`,
чтобы одно сообщение не затирало поля другого.

Gateway также видит другие сообщения на общей multicast-группе, например
`dbg` и `ptp_state`, но не выдаёт их за `dcu_tel`: неподдерживаемый MicroJet ID
отклоняется до передачи в Backend.

### Внутренний TLV Gateway → Backend

Все числа little-endian:

```text
uint8  type
uint16 src_id
uint16 dst_id
uint32 ts_s
uint32 ts_ns
uint16 payload_length
bytes  payload[payload_length]
```

Размер заголовка — 15 байт. Это внутренний фрейм приложения, а не полный raw
Ethernet-пакет.

## Обратный канал управления

Backend отправляет управляющие фреймы обратно по тому же TCP-соединению 8888.
Gateway проверяет заголовок, назначение и размер, а затем использует готовые
generated-функции `cmd_req.tx(dst)`, `msg_req.tx(dst)` и `prm_req.tx(dst)`.
Собственный формат MicroJet Dashboard не придумывает.

В интерфейсе нет выбора `DST=ALL`. Устройство назначения всегда определяется
карточкой одного из шести `bup_dcu_*`. Доступны:

- чтение и запись 71 generated-параметра МУП с правильной бинарной упаковкой типов;
- чтение всех параметров последовательными запросами;
- `SAVEPRM` и остальные generated-команды;
- запрос `bup_state` и электронного формуляра;
- сервисное управление одного привода через `bup_srv_ctrl` с периодом 20 мс.

Backend поддерживает lease сервисного режима, а Gateway независимо проверяет
его срок. При закрытии управляющей вкладки, разрыве TCP или завершении Gateway
передача переводится в `OFF`, после чего выключается. Подробности находятся в
`REVERSE_CHANNEL_IMPLEMENTATION.md`.

### WebSocket schema v1

Backend передаёт события в конверте:

```json
{
  "schema_version": 1,
  "type": "telemetry_batch",
  "sent_at": "2026-08-09T12:00:00+00:00",
  "payload": {}
}
```

Основные типы событий:

- `telemetry_batch` — окна по 100 мс со статистикой `mean/min/max/last/count`;
- `devices_batch` — полные последние сообщения для карточек, обычно 2 раза/с;
- `devices_snapshot` — состояние устройств, внутри каждого сообщения разделены по `msg_type`;
- `telemetry_history` — последние агрегированные окна для начального графика;
- `system_status` — соединение Gateway и счётчики пакетов;
- `recording_status` — единое состояние записи телеметрии для всех вкладок;
- `recordings_list` — каталог законченных и прерванных записей;
- `control_catalog` — generated-каталог параметров, команд, сообщений и режимов;
- `control_snapshot` — прочитанные параметры и состояние сервисного управления;
- `control_response` — подтверждение Gateway или ответ контроллера;
- `script_result` — stdout, stderr, exit code и время выполнения скрипта.

Один общий WebSocket обслуживает все вкладки, но события сначала разделяются
в браузере. `telemetry_batch` попадает прямо в Plotly и не запускает
Python-callback вкладок «Устройства» и «Скрипты». Полные значения в карточке
устройства обновляются не чаще одного раза в секунду, хотя Backend продолжает
передавать `devices_batch` два раза в секунду.

Надпись `ONLINE` на карточке означает именно наличие свежих пакетов этого
устройства. Она считается в браузере непосредственно по `devices_batch` и не
зависит от очереди перерисовки. Поле `status` из MicroJet — отдельный
протокольный параметр и показывается внутри раздела «Состояние»; значение
`UNKNOWN` в нём больше не превращает сетевой индикатор в непонятный статус.

Команды управления архивом: `start_recording`, `stop_recording`,
`get_recording_status` и `list_recordings`. Таймер выполняется Backend, поэтому
обновление или закрытие браузера не прерывает запись.

### Как обновляется живой график

Полный поток `dcu_tel` не передаётся в браузер точка в точку. При периоде
250 мкс это было бы 4000 сообщений/с от одного источника и до 40 000 сообщений/с
от нескольких источников.

Независимо от состояния записи Backend собирает для UI окна по 100 мс. Для
каждого числового поля окно содержит:

- среднее значение;
- минимум и максимум;
- последнее значение;
- количество исходных пакетов.

Поэтому одна линия получает около 10 новых точек в секунду. График по умолчанию
показывает последние 10 секунд. Поля «Окно, с» и «Назад, с» задают длительность
и смещение от последних данных. «Пауза» фиксирует данные для изучения, не
останавливая приём или запись; после паузы можно задать точные границы «От» / «До»
в UTC. «К последним данным» возобновляет слежение без смещения.

Сигналы добавляются в боковой панели, где указаны понятное название, источник
`dcu_tel` / `bup_state`, цвет и последнее значение в выбранном интервале.
Можно скрыть отдельную линию или удалить группу; фазные токи добавляются вместе,
но видимость A/B/C переключается отдельно. Разные единицы измерения используют
отдельные вертикальные шкалы с автоматическими или ручными пределами.
Набор сигналов, диапазон и настройки шкал сохраняются отдельно для каждого
устройства до перезагрузки страницы. Масштабирование по времени мышью включает паузу.

Браузер хранит до 216 000 агрегированных точек на сигнал. Отрисовка обновляется
до четырёх раз в секунду и получает только выбранный интервал с граничными
точками. Полоса `min–max` включается отдельно и показывает разброс внутри
100-миллисекундного окна, линия показывает среднее. Отсутствующие значения
отображаются как «—», а не как ноль.

Ось X использует `ts_s + ts_ns` из MicroJet-заголовка и показывает его как
обычное календарное время с секундами и миллисекундами. Токи фаз A, B и C
остаются отдельными полями протокола, но выводятся одним пунктом выбора как три
цветные линии. Последний одиночный `bup_state` восстанавливается в график из
снимка устройства даже после выхода события из короткой истории частого
потока.

Для углов около границы `-π/+π` используется круговое среднее. Если окно
пересекает эту границу, линейная полоса `min–max` для него скрывается, потому
что иначе она ошибочно закрыла бы почти весь диапазон графика.
Если тестовый источник передал одноповоротный угол вне заявленного диапазона
`-π…+π`, значение не сворачивается молча: график показывает исходное число и
выводит предупреждение. Многооборотный `bup_state.rotor_sens_angle` считается
линейной величиной и также не сворачивается.

## Запись данных и логи

По умолчанию сырая телеметрия на диск не пишется. Кнопка «Начать запись»
сразу запускает запись до ручной остановки. «Остановить запись» завершает
файл; затем кнопка снова становится «Начать запись», а рядом появляется имя
сохранённого PKL. Состояние проверяется независимо от потока WebSocket.

Переключатель «Прямой эфир / Записи» открывает каталог файлов. Выберите имя
и нажмите «Открыть»: сохранённые данные появятся на том же графике. Доступны
выбор устройства и сигналов, масштаб, точные даты, ползунок позиции, переход
по окнам и показ всей записи. «Прямой эфир» возвращает к последним данным.
Приём и текущая запись продолжаются во время просмотра архива.

«Скачать PKL» скачивает исходный файл без преобразования. «Удалить» после
подтверждения убирает запись из списка и переносит файл в `recordings/.trash`;
метаданные остаются в каталоге со статусом `deleted` для ручного восстановления.
Активные записи удалить или открыть нельзя.

При первом открытии PKL отдельный процесс создаёт индекс просмотра в
`recordings/.preview`. Сырые данные остаются в PKL. Индекс содержит окна
по 100 мс; большие выбранные интервалы дополнительно объединяются до примерно
1500 точек на тип сообщения с сохранением min/max. Узкий интервал можно
изучить подробнее. Файлы загружаются только из локального каталога записей,
импорт произвольных PKL не предусмотрен.

Служебный HTTP API Backend слушает только `127.0.0.1:8766`; браузер обращается
к нему через `/api/recordings/` на frontend. Скачивание идёт потоком, не загружая
весь файл в память браузерного JavaScript или Dash callback.

Одна сессия содержит все TLV-кадры, поступившие от всех устройств за выбранное
время, и сохраняется в отдельный файл:

```text
backend/storage/recordings/
├── index.json
└── YYYY-MM/
    └── rec_YYYYMMDDTHHMMSSZ_1234abcd.pkl
```

Во время работы используется расширение `.pkl.part`. При остановке Backend
сначала прекращает принимать новые кадры в архив, дописывает очередь, выполняет
`flush/fsync`, закрывает файл и атомарно переименовывает его в `.pkl`. Только
после этого запись отмечается законченной в `index.json`.

Внутри PKL кадры объединены в блоки формата
`bro30-recording-batch-v1`. Каждый элемент содержит UTC-время приёма в
наносекундах и исходный внутренний TLV целиком. Это не Ethernet-кадр:
Ethernet/IP/UDP и внешняя часть MicroJet уже обработаны Gateway.

`index.json` хранит ID и название сессии, время начала/окончания,
продолжительность, размер, количество пакетов, статистику по сообщениям и
устройствам, причину остановки и признак неполной записи. Каталог обновляется
атомарно и имеет резервную копию `index.json.bak`. Незаконченная после аварии
`.part`-сессия при следующем запуске отмечается как `interrupted`.

Backend оценивает размер ограниченной по времени записи по текущей скорости
потока и следит за диском во время работы. По умолчанию он оставляет резерв
10 ГБ и завершает запись с ошибкой при достижении этого порога. Старые записи
автоматически не удаляются. Резерв можно настроить перед запуском:

```bash
export RECORDING_MIN_FREE_GB=20
```

Просмотр каталога и экспорт доверенной записи:

```bash
python3 backend/tools/recordings.py list
python3 backend/tools/recordings.py info 1234abcd
python3 backend/tools/recordings.py verify 1234abcd
python3 backend/tools/recordings.py export 1234abcd --limit 100 --format json
python3 backend/tools/recordings.py export 1234abcd --device bup_dcu_lfd \
  -o telemetry.jsonl
```

JSONL используется по умолчанию и подходит для больших записей: каждый пакет
выводится отдельной строкой без загрузки всего файла в память.

`backend/storage/logs/backend.log` содержит операционные сообщения Backend и
работает независимо от записи телеметрии. Он ротируется при размере 10 МБ;
хранятся пять предыдущих файлов.

`pickle` нельзя открывать из недоверенного источника: при загрузке он способен
выполнить содержащийся в файле Python-код.

## Python-скрипты

Редактор выполняет обычный код без обязательной функции `process`:

```python
a = 10
b = 20
print(a + b)
```

Код запускается отдельным Python-процессом с таймаутом 5 секунд. UI показывает
stdout, stderr, exit code и длительность. Это защита Backend от зависания, но не
полная security-песочница; стенд считается локальным и доверенным.

## Диагностика

```bash
docker compose logs -f gateway
docker compose logs -f backend
docker compose logs -f frontend
```

Gateway раз в несколько секунд выводит агрегированную статистику:

```text
[PKT] total rx=... fwd=... no_backend=... reject(header=... id=... size=... src=... ts=...)
```

Это позволяет отличить отсутствие трафика от неверного ID/размера и от
отключённого Backend без записи строки на каждый пакет.
